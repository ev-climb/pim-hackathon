# Настройка и деплой: путь, которым это прошли

Всё, что делается руками, от пустого проекта до работающего прода. Не план, а протокол: каждый шаг выполнен, каждая грабля собрана лично. Порядок важен — часть значений нужна на следующем шаге. Чистое время около 45 минут, половина уходит на Google Cloud.

Выписывай значения в менеджер паролей, в конце сводка.

**Текущий экземпляр:** Supabase-проект `azswlqiwsdybrploejzj`, репозиторий `ev-climb/pim-hackathon`, локальный порт `5174`.

## B. Схема базы

**SQL Editor** → выполнить `supabase/schema.sql` четырьмя блоками, они помечены `-- ==== N ====`.

> **Главная грабля.** Редактор выполняет **всё содержимое вкладки**, а не то, что вставили последним. Если дописать блок 2 под блок 1 и нажать Run, первый блок отработает повторно и запуск упадёт на `42710: type "category" already exists`. Причём содержимое вкладки идёт одной транзакцией, поэтому после такой ошибки новый блок не применится вообще.
>
> Лечится одним из двух: **чистить вкладку целиком** (Ctrl+A, Delete) перед каждым блоком, либо держать весь файл в одной вкладке и **выделять нужный блок мышью** — выделенное выполняется отдельно.

На блоке 1 Supabase спросит про RLS: «This query creates tables without enabling Row Level Security». Жать **Run and enable RLS** — блок 4 включает её сам, повторное включение безвредно, а «Run without RLS» оставила бы таблицы открытыми в промежутке между блоками.

**Проверка, работает на любом этапе:**

```sql
select
  (select count(*) from information_schema.tables where table_schema='public')                  as "таблиц и вью",
  (select count(*) from pg_policies where schemaname='public')                                  as "политик",
  (select count(*) from pg_trigger where tgrelid='auth.users'::regclass and not tgisinternal)   as "триггер входа",
  (select count(*) from pg_trigger where tgrelid='public.votes'::regclass and not tgisinternal) as "триггер бюджета";
```

| После блока | таблиц и вью | политик | триггер входа | триггер бюджета |
|---|---|---|---|---|
| 1 — таблицы | 5 | 0 | 0 | 0 |
| 2 — функции и триггеры | 5 | 0 | 1 | 1 |
| 3 — вью | 7 | 0 | 1 | 1 |
| 4 — права и политики | 7 | **13** | 1 | 1 |

Больше 7 в «таблицах и вью» — нормально, Supabase держит в `public` кое-что своё. Важно, чтобы не было **меньше**, а политик было ровно 13.

Ошибка `already exists` при повторном запуске означает, что блок уже применён: объект есть, а транзакционность гарантирует, что применился он целиком.

**Если база уже создана по прежней версии схемы**, `schema.sql` заново не запускается — на неё накатываются миграции из `supabase/`, по порядку номеров, теми же блоками в чистой вкладке:

| Файл | Что добавляет |
|---|---|
| `migrate-01-edit-delete.sql` | правку и удаление своей идеи (`update_my_idea`, `delete_my_idea`), `ideas.edited_at`, описание до 500 символов, новые колонки `ideas_public` |

Миграции идемпотентны, повторный запуск безвреден, последний блок каждой печатает ожидаемые числа. Количество политик при этом не меняется — их по-прежнему 13. После добавления функций PostgREST обновляет кэш схемы сам; если `rpc` отвечает «Could not find the function», это лечится кнопкой Settings → API → **Reload schema cache**.

## C. Организаторы

Список админов живёт в `app.is_admin()` — просто перечисление почт. **Перед первым запуском блока 2 впиши туда реальные адреса** вместо заглушки.

Правится **только через `create or replace`**: на функцию опираются 13 политик, `drop function` упрётся в зависимости, а `cascade` снёс бы политики вместе с ней. Замена тела при неизменной сигнатуре проходит спокойно, дропать ничего не надо.

**Каждого человека вносить в обоих доменах.** Люди заходят то с `@pimpay.ru`, то с `@pimsolutions.ru`, а признак админа считается по адресу из JWT. Актуальный список — в `supabase/schema.sql`.

Проверка:

```sql
select set_config('request.jwt.claims', '{"email":"кто.то@pimpay.ru"}', true), app.is_admin();
```

Два следствия:

- **Перезагрузка страницы обязательна.** Признак админа приходит один раз при старте через `me()` и лежит в сторе. В базе права действуют сразу, заново входить не нужно, но вкладка «Рейтинг» появится только после обновления.
- **Второй адрес — отдельный человек для базы.** `auth.users` различает людей по адресу, а не по имени. Организатор, зашедший с двух почт, получит два профиля с двумя бюджетами по 5 голосов. Для просмотра рейтинга неважно; если он ещё и голосует — договоритесь, с какой почты.

Меняешь список — **поменяй адрес и в `supabase/test/01-checks.sql`**, там он зашит для проверок 12 и 13. Иначе они отвалятся с «почта из списка не даёт админа». Предупреждение стоит в шапке файла.

## E. Google Cloud: OAuth (15 минут)

console.cloud.google.com → новый проект. Биллинг не нужен, кредиты и кнопку Upgrade игнорировать.

Раздел называется **Google Auth Platform** (бывший OAuth consent screen): APIs & Services → OAuth consent screen. **Никакие API включать не надо** — ни People API, ни что-либо ещё, это лишний совет из туториалов.

**E1. Branding:** App name, User support email, Developer contact — рабочая почта. Логотип, домены, ссылки на политики пропустить.

**E2. Audience: брать External.**

Internal покрывает только пользователей той Google-организации, к которой привязан проект. У нас проект в организации `pimpay.ru`, а большинство сотрудников на `@pimsolutions.ru` — при Internal они получили бы `org_internal` и не вошли бы вовсе. External покрывает оба домена независимо от того, как устроены организации, а со скоупами `openid`/`email`/`profile` верификация Google не нужна и пугающего экрана «приложение не проверено» не будет. Домены всё равно режет триггер в базе, а не Google.

> **Грабля.** Кнопка **Publish app** живёт на странице **Audience**, а не на Overview, куда выбрасывает после создания конфигурации. Без неё приложение остаётся в состоянии **Testing**, где войти могут только вручную добавленные тестовые пользователи, максимум 100. Статус должен стать **In production**.

Поле Authorized domains можно не заполнять: приложение живёт на `supabase.co` и `vercel.app`, они у Google в доверенных.

**E3. Data Access:** только `openid`, `email`, `profile` — или вообще пусто, Supabase запросит их сам. Любой чувствительный скоуп запускает верификацию Google на недели.

**E4. Clients → Create client:**

- Application type: **Web application**
- Authorized JavaScript origins: **пусто**
- **Authorized redirect URIs — ровно одна строка,** колбэк Supabase из A2

Адрес приложения (`localhost`, Vercel) сюда **не добавлять**: браузер возвращается на Supabase, а тот перекидывает дальше. Это второе по частоте место, где всё ломается — расхождение даёт `redirect_uri_mismatch`.

Client ID и Client Secret скопировать сразу, secret потом только пересоздать.

## H. GitHub

Создать **пустой** репозиторий, без README и .gitignore, иначе придётся разбирать расхождение историй.

```bash
git init -b main
git add -A
git commit -m "…"
git remote add origin git@github.com:<аккаунт>/<репозиторий>.git
git push -u origin main
```

Ключ добавляется в **Settings → Deploy keys → Add deploy key** самого репозитория, с обязательной галочкой **Allow write access**. Deploy key видит один репозиторий — уже, чем ключ аккаунта. Один и тот же ключ нельзя использовать как deploy key в двух репозиториях и как ключ аккаунта одновременно, поэтому под проект генерируется своя пара без пароля:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_pim_hackathon -N "" -C "pim-hackathon deploy key"
```

> **Грабля, которая съела больше всего времени.** Push падал с `Permission to … denied to deploy key`, хотя ключ с правом записи был добавлен правильно.
>
> Причина: в `~/.ssh/config` для `github.com` жёстко прописан `IdentityFile` другого ключа, и он же загружен в ssh-agent. SSH предлагал его **первым**, GitHub его принимал — и вся сессия шла от имени deploy key чужого репозитория, у которого здесь только чтение.
>
> `IdentitiesOnly=yes` это **не лечит**: ключ из `~/.ssh/config` тоже считается явным и добавляется к переданному через `-i`. Из-за этого врала и диагностика — `ssh -i новый_ключ -T git@github.com` отвечал приветствием чужого репозитория, хотя новый ключ был в полном порядке.
>
> Лечится полной изоляцией. Записывается локально для репозитория, дальше `git push` работает обычной командой:
>
> ```bash
> git config core.sshCommand "ssh -F /dev/null -o IdentitiesOnly=yes -o IdentityAgent=none -o StrictHostKeyChecking=accept-new -i ~/.ssh/id_ed25519_pim_hackathon"
> ```
>
> `-F /dev/null` игнорирует пользовательский конфиг, `IdentityAgent=none` отсекает агента — остаётся ровно один ключ из `-i`.
>
> Диагностика, которая показывает правду: `ssh -v … -T git@github.com 2>&1 | grep "Server accepts key"`. Плюс приветствие GitHub: `Hi username!` — ключ аккаунта, `Hi owner/repo!` — deploy key этого репозитория.

## I. Vercel (5 минут)

vercel.com → **Add New → Project** → импортировать репозиторий. Если он не виден, дать доступ GitHub App — можно только на этот репозиторий, весь аккаунт открывать не нужно.

Определяется само, проверить:

| Поле | Значение |
|---|---|
| Framework Preset | **Vite** |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Root Directory | пусто |

**Environment Variables** — две, для **всех** окружений (Production, Preview, Development), иначе превью-деплои падают с ошибкой про отсутствующий ключ:

```
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
```

Ключ публичный и попадает в бандл — так задумано, данные защищают политики доступа. `service_role` сюда не вставлять ни при каких обстоятельствах.

Deploy. Сборка около минуты, основное время — `npm install`. Получишь адрес вида `pim-hackathon.vercel.app`.

> **Важно про клиентский роутинг.** Vercel **не** добавляет SPA-фолбэк для Vite — его документация прямо говорит «deep linking won't work out of the box». Без переписывания запросов `/ideas` и `/admin` отдают 404 при прямом заходе и при обновлении страницы; проверено на статике локально. Поэтому в корне лежит `vercel.json` с одним правилом «любой путь → `index.html`». Файл подхватывается автоматически, в дашборде настраивать нечего. Без него приложение работало бы ровно до первого F5.

Дальше каждый push в `main` деплоится сам.

## K. Проверка на проде

1. Адрес Vercel в приватном окне → экран входа.
2. Вход с рабочей почты → `/ideas`, имя из Google-профиля, «Осталось голосов: 5 из 5».
3. **F5 на `/ideas`** → не 404. Если 404 — не подхватился `vercel.json`.
4. `/admin` напрямую → рейтинг с почтами (для адреса из списка организаторов).
5. **Вход двумя людьми, по одному с каждого домена.** Единственный пункт, который нельзя закрыть в одиночку, и именно здесь вылезает `org_internal`, если домены в разных Google-организациях. Не откладывать: чинится одним переключением Audience.

Из консоли браузера под обычной учёткой — то, что попробует любопытный коллега:

```js
await supabase.from('ideas').select('*')     // пусто: доступа к таблице нет
await supabase.from('profiles').select('*')  // только своя строка
```

Без входа вообще всё закрыто, проверено на живом проекте:

```
ideas_public → 42501 permission denied for view ideas_public
ideas        → 42501 permission denied for table ideas
profiles     → 42501 permission denied for table profiles
```

Правила из §4 прогоняются автоматически — `supabase/test/01-checks.sql`, 29 проверок: приватность, бюджет голосов, блокировка, модерация, правка и удаление своей идеи. Работает на Postgres 16 и 17.

```bash
docker run -d --name pimtest -e POSTGRES_PASSWORD=pw -v "$PWD/supabase":/sb:ro postgres:17-alpine
docker exec pimtest psql -U postgres -q -v ON_ERROR_STOP=1 -f /sb/test/00-stub.sql
docker exec pimtest psql -U postgres -q -v ON_ERROR_STOP=1 -f /sb/schema.sql
docker exec pimtest psql -U postgres -f /sb/test/01-checks.sql
docker rm -f pimtest
```

Набор **вставляет свои данные и рассчитан на пустую базу** — повторный запуск в том же контейнере упадёт на дубликате ключа, это не поломка. Для повторного прогона поднимать контейнер заново.

## L. Перед публикацией опроса

Зачистить тесты — `supabase/reset.sql`. Блок 1 показывает, что накопилось, блок 2 удаляет, блок 3 проверяет.

**Профили живых людей удалять нельзя.** Профиль создаётся триггером один раз, при первом входе. Удалишь строку из `profiles` — повторно она не появится: триггер висит на `insert into auth.users`, а такая запись уже есть. Человек получит пустое имя и отказ при публикации идеи. Удаляются только демо-люди из сида.

Автобэкапов на Free нет — перед запуском на людях сделать дамп руками.

- Проект **встаёт на паузу после недели без запросов**. Будится кнопкой в дашборде, данные не теряются. Если между настройкой и рассылкой пройдёт время — разбуди до того, как коллеги пойдут по ссылке.
- Автобэкапов на Free нет. Перед запуском на живых людях сделай дамп руками.
- Лимиты (500 МБ, 50 тысяч активных пользователей в месяц) для тридцати человек несопоставимо велики.
